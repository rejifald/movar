# @movar/audit

## 0.2.0

### Minor Changes

- 2d99090: Give the audit CLI a `--warm` flag, so the cookie-override rule can finally run.

  `core/serving-cookie-overrides-header` has been in family C since the serving rules landed, and had never adjudicated anything. The prober could keep a cookie jar, cold-vs-warm was unit-tested, and the rule was written and covered — but `collectNetwork` exposed no way to ask for a warm leg and the CLI had no flag, so every real run read `not-applicable` and the rule was unreachable from any command. `docs/movar-audit-dogfood-targets.md` logged it as a CLI-surface gap after the eight-site pass; this closes it.

  **A warm leg is a second matrix, not a warmer first one.** A matrix leg is `(url, vantage, cookieState)` — `matrixLegKey` in `capability.ts` says so, and every family-C rule groups by it. Warming the one leg in place would not hand this rule a warm reading to look at; it would delete the cold reading the warm one is compared _against_, and take the header differential the other six rules are adjudicated from with it. So `--warm` collects the same headers twice: the cold matrix exactly as before, then a warm one beside it. The rule wants both halves of one `Accept-Language`, and now gets them.

  **The jar belongs to the run, which is the bug that made "warm" not warm.** It was constructed inside `probe()`, handed to the redirect walk empty and thrown away, so every request still went out cold and only a chain of redirects ever carried a `Cookie` header. What the rule asks about is a **stored** cookie outranking an explicit preference, and no such cookie exists until one probe's `Set-Cookie` reaches the next probe. `createProber` now keeps one jar, built on the first warm probe and never before it — a cold prober must not so much as own the thing whose absence is what makes its legs comparable.

  **The warm leg opens with a request that states no preference**, and that is the whole design rather than an ordering detail. A jar warmed by `Accept-Language: uk` holds whatever cookie _our own header_ talked the site into setting, so a warm `uk` probe answered in Ukrainian demonstrates nothing at all. The question is whether the language the site chose **on its own** outranks a preference stated afterwards, and asking for nothing is how the site is left to choose. Only the URL the operator typed goes warm: `robots.txt` and the declared targets keep the cold default, so no cookie this run collected is ever presented to an origin nobody typed, and the expansion stays the unauthenticated page view the network posture documents.

  **The run's posture is stamped on the evidence** — `NetworkSource.cookies`, `schemaVersion` 6, optional so a stored bundle still replays. ADR §4 requires cold by default because a warm session is precisely the difference the matrix's _everything-else-identical_ promise has no room for, and a reader has to be able to see which run they are holding. It is recorded rather than derived from the probes because those two are not the same claim: a warm leg that met a challenge interstitial, failed in transport, or was priced out by the cold matrix ahead of it leaves a bundle whose probes are **all cold**, and reading "this was a cold run" off that hands the collector's own luck to the operator as their choice — quietly retiring a rule they opted into. The rule's `notApplicable` reason forks on exactly that, and now says "this run asked for a warm cookie leg, and no warm probe survived to be adjudicated" instead of describing it as cold.

  The budget is the same hard ceiling, re-read before every warm probe and never reserved out of the cold pass. A budget too small for both therefore buys the cold matrix, which is the right way round — it is the leg the other six family-C rules need — and the posture on the evidence is what keeps that shortfall visible rather than silent.

  Covered end to end against a synthetic site that decides by cookie: cookie-free it honours `Accept-Language`, and once its own `lang=ru` comes back to it, it answers Russian whatever the header says. Driven through `CORE_RULESET`, because that is the shape of the defect — every collector field looked right while the verdict a site owner reads never moved. The same site with no `--warm` still reads `not-applicable`, so the finding is the flag's doing rather than the fixture's.

### Patch Changes

- 82a55ff: Resolve a declared target against the build path when the page has no URL.

  `resolveTargetPage` threaded `from.url` as `parseLocator`'s base, and `PageEvidence.url` is documented "present on network evidence" — a page collected off disk carries `path` instead. So `new URL(href, undefined)` could not resolve, and every relative href on filesystem evidence fell back to the site-root reading #430 removed for pages that do carry a url: `../uk/guide.html` declared on `/docs/en/guide.html` became the literal path `/../uk/guide.html`, and a bare `./` self-reference became `/.`. #430 fixed exactly this defect for network evidence and left the filesystem case out of scope.

  **The dogfood gate over `apps/marketing/dist` is filesystem evidence** — the path Movar audits itself on was the one still carrying the defect. Any site audited from a build directory got the pre-#430 behaviour: a relative alternate false-failing `core/hreflang-target-unresolvable`, which is a `fail` published against markup `core/hreflang-target-relative` only _warns_ about, so the catalogue expects it.

  `declaredLocator(page, href)` is now the one place that base is decided, and every family reads a declared href through it — the local copy in `inventory-hreflang.ts` that passed `page.url` is gone, and so is the same expression in `switch.ts` and `ua.ts`. A build path is lifted into the **non-special** `movar-build:` scheme, which is the whole of the design: relative resolution folds `..` exactly as a browser does, and the lifted base reports an _empty host_, which `parseLocator` now reads as `null` like any other host-less locator. An `https://` stand-in fabricates an origin the page never claimed, and `locatorOf` reads a page's own location through the same lift — so the synthetic host would land on every page in the build, `sameLocation` would weigh it against the real host each absolute href names, and no absolute alternate would resolve to a collected page at all. That is the dogfood gate's own shape, where every hreflang is absolute and every page is a build path.

  `locatorOf` reads a page's own path through that lift too, so both sides of a comparison are percent-encoded by one `URL` parse. Read raw, a page at `/пошук/` spelled its path literally while every declared href spelled it `/%D0%BF…`, and no alternate naming it — relative or absolute — could resolve to it.

  The build path is spelled for the lift before it happens. `#` and `?` are percent-encoded, because both end a URL's _path_: `collectFilesystem` takes any `*.html` name, so `a#b.html` and `a#c.html` would each truncate to `/a`, become one locator, and have `ua/state-language-version-lesser` count the pair as a single page. And leading slashes collapse to one, because `movar-build://evil.example/uk/index.html` opens an _authority_ and hands a build page a host it never had — unreachable from `collectFilesystem`, which joins exactly one slash, but it is precisely the fabricated origin the scheme was chosen to prevent, and it must not arrive through the scheme itself.

  The resolver is shared, so the verdicts move in three families, in both directions:
  - **B** — `core/hreflang-target-unresolvable` passes a relative alternate that resolves, and `core/hreflang-self-missing` stops warning that a page declaring `./` is missing from its own translation set.
  - **D** — `core/switch-no-effect` and `core/switch-loses-path` adjudicate a build's relative targets instead of reading `not-applicable` on "no declared target resolved": a switch that serves the source language again is now a `fail`, and one that keeps its path is now the `pass` it was owed.
  - **F** — `ua/state-language-version-lesser` joins a build's duplicated version through a relative alternate, so a build at exact 1:1 parity is no longer published as ru 2 / uk 1 with Law 2704-VIII cited on it; and it measures a paired volume deficit that off disk was never compared at all.

  One existing test changed rather than being added to: `core/hreflang-target-unresolvable`'s "resolves targets on a filesystem build" declared `href="ru/index.html"` from `/uk/index.html` and expected it at `/ru/` — the site-root reading, which is the defect. A browser reads that href as `/uk/ru/index.html`; the fixture now says `../ru/index.html`, which is what the site meant.

  The dogfood gate is unchanged: `apps/marketing` emits absolute hreflang hrefs, has no picker, and no route on it is non-ASCII.

- 1463e3b: Digest a redirect's destination with the destination's own headers, and let the request budget end a chain instead of the audit.

  Two defects in the redirect-walking collector, landed together because they are the same seam: `probe()` records one observation about **two resources**, and each caller has to name which one it means.

  **A redirect's `Link` header was stamped onto the page it points at.** `ProbeEvidence.responseHeaders` is deliberately the **first** response's — `core/serving-vary-missing` asks about the resource a shared cache stores for the probed URL, and a locale-autodetect `302` at `/` is that resource, while the `/uk/` page behind it is a fixed-locale URL that correctly does not vary. That field stays exactly as it is. It was simply the wrong field to read the _destination document's_ declarations from: `addPage` handed it to `createPageSet`, which parsed its `Link: …; rel="alternate"` and its `Content-Language` into the digest of the page at the **end** of the chain. Two resources' declarations in one `DocumentEvidence`, and `core/inventory-sources-disagree` then published the collector's own merge as a defect of the site — a `302` carrying `hreflang="de"` in front of a page declaring only `hreflang="uk"` failed **twice**, once per direction, about two resources neither of which disagrees with itself. That is a false `fail` naming a real site, produced entirely by the collector.

  `ProbeEvidence.finalResponseHeaders` (`EVIDENCE_SCHEMA_VERSION` 6, additive and optional) now records the destination's, and `documentHeadersOf` in `collect/assemble.ts` is the one place the pair is read back — beside `finalUrlOf`, which answers the same question about the URL. It is written **only where the chain redirected**: on an empty chain the first response _is_ the serving one, so a byte-for-byte second copy on every probe of every bundle ever stored would say nothing new — the same reasoning that keeps `redirectChainTruncated` out of every untruncated probe. Where a chain redirected and no destination headers were recorded — a pre-v6 bundle, or `AuditProbe.swift`, which sends only the first response's today — the helper answers `undefined` and the document is digested with **no** header declarations. That is the honest degradation: an alternate the collector did not collect is a gap, one taken off another resource is an accusation. It lives in `assemble.ts` rather than in each collector for the reason that module exists — two runtimes answering "which headers are this document's?" differently report different findings about the same site — so `@movar/audit-engine`'s WebView collector is fixed by reading the same helper, with no protocol change and no native work.

  **A budget reached mid-chain killed the audit instead of ending the walk.** `spend()` sits inside the per-hop fetch, so one `probe()` costs anywhere from 1 to `maxHops + 1` requests and a redirecting target can hit the ceiling on a hop nobody could have predicted; `RequestBudgetExhaustedError` then came out through `collectNetwork` and took the whole run with it. Measured across 1080 randomized configurations during the #481 review, it threw on 119 — a user who set a tight `--budget` on a site with a redirecting alternate got a crash instead of a partial report. The error's own sentence is the argument against that: an audit must _state_ what it did not fetch, and a crash states nothing at all. `walk` now stops at the budget exactly as it stops at `maxHops`, answering with the chain it has and the last 3xx it really got.

  **One flag for both ceilings, not a sibling.** A budget-ended chain sets `redirectChainTruncated`, the vocabulary #482 established. What a rule needs to know is whether the walk saw where the chain ended, and neither ceiling did; a second flag would mean every reader has to remember to ask twice, and the reader that forgot would publish `pass` off a chain nobody saw the end of — the exact defect #482 closed, reopened on the budget path. _Why_ the walk stopped is the operator's business (raise `--budget`, raise `maxHops`) and not a different fact about the site — and no reader needs to know: the bundle deliberately does not say, since `maxHops` is not on the wire and a bundle is adjudicated by a kernel that never saw the collector that wrote it. So `core/switch-bounces` publishes it as the same `observed` `warn`, naming the hops it did see and never claiming to know where the chain landed.

  **Finishing the run means every rule now answers about a chain nobody walked to its end, and one of them was accusing the site for it.** `core/hreflang-target-unresolvable` resolves a declared target against the collected page set, and a truncated chain produces no page — nobody fetched the URL the last hop named — so it published a `declared` **fail**, _"the declared alternate cannot be reached"_, in the same report as the `core/switch-bounces` warn saying reachability _was not determined_. Two findings contradicting each other about one site, and the accusing one carried the verdict; before this change the crash meant no report existed to contain them. It withholds that finding on the flag now, so the warn is the only thing said about such a target. **Withholding is not passing**: the page reads `not-applicable` rather than `pass`, and nothing in the report claims the target resolves. The same defect was older than the budget path — an 11-hop chain sets the same flag and failed here too — and the one check covers both ceilings.

  The **first** hop of a probe still throws. Asking for a probe the budget cannot pay for at all is a caller that did not read `remaining()`, not an observation about a site, so the graceful stop never degrades into the silent cap `RequestBudgetExhaustedError` exists to prevent — and `collectNetwork` and `followDeclared` both check the ceiling before they ask.

- eb7469c: Put the served-language seam behind the text-sample gates it was written to obey.

  `text-samples.ts` exists so that "may this snippet be classified at all?" has exactly one answer — its module doc says so in as many words, because two copies of that question drift into two answers to the only thing that decides whether a passage gets cited in a published document naming a company. Families A and E asked it through `classifySamples` and were gated. Families C, D and F did not: `served-language.ts`'s `classifiedPageLanguage` and `ua.ts`'s `classifyDefaultLanguage` each ran their own majority vote straight over raw `sample.text`, outside the 40-character floor, outside the proper-noun-run exclusion, and outside the `<code>` / `<samp>` / `<kbd>` exclusion. Three samples — two two-character words and one `<code>` node — kept zero passages through the shared gate and produced `{"language":"uk","via":"classified","denominator":{"examined":3,"matched":2}}` at the seam.

  **`via: 'classified'` is why this stayed invisible, and not why it was harmless.** The kernel strips such a finding of its failing power, so nothing ever went red. But the observation is still published, still names a site, and still rests on text the catalogue's own gates call unclassifiable — and in `core/switch-no-effect` the determination is not merely reported, it is the test: `served?.language !== source` returns no draft at all, so a fabricated verdict naming any other language silently suppresses a finding that may have been real. Family F is the sharper end of the same thing, since `ua/state-language-not-default` stamps Law 2704-VIII on what it publishes: a page whose only passage was a title-cased product line ("Московский Инструментальный Завод Ударные Дрели Российское Качество") classified as Russian and drew a statute-citing summary.

  The page-level vote now lives once, as `dominantSampleLanguage(classify, page, candidates)` in `text-samples.ts` — `classifySamples` for the gates, the majority count, and `textNodeDenominator` for the share — and both call sites are two lines over it. The two hand-rolled vote loops it replaces were already character-for-character equivalent, which is exactly how the gates went missing from one of them and not the other. The denominator is unchanged and still states the population the walker examined: the exclusions narrow what is _classified_, never what is _counted_, since every one of them runs in the direction of the accusation.

  `classifySamples` grows an optional `candidates` argument defaulting to `CLASSIFIER_CANDIDATES`, which is what families C, D and F need to keep asking their own question — "of the languages this site **declares**, or this switch names, which one came back?" — without answering it about Bulgarian. That default is load-bearing rather than decorative: the widest roster makes the classifier abstain where a narrow pair commits, so the brand string above is `null` against `uk/ru/be/bg/en` and `ru` against `uk/ru`. The gates themselves take no parameter and must not grow one.

  **Some findings correctly disappear.** Any family C, D or F observation that rested on a passage under the floor, on a run of proper nouns, or on the contents of a `<code>` block is now no finding at all — the rule reads `not-applicable` where it used to publish. That is the catalogue's under-firing bias arriving somewhere it had never been applied, and the test fixtures that had to grow real prose are the measure of how much of that path was running on text nobody should have classified.

- a46a5cf: Stop a suppression entry's validity depending on whether the run collected its rule, and guard the catalogue property the check rests on.

  `subjectScopeProblem` decides doctrine 2 — a rule whose findings name a page must name the page it is silenced on — off the **findings**, because a rule's `scope` says how the kernel iterates it and a finding's says what the finding is about. When a rule emitted no findings it fell back to the rule's own scope, and that fallback was the same conflation one step removed. Family C declares `site` and emits `page`, so `{ rule: 'core/serving-header-ignored', subject: 'https://x.test/a' }` was legal against a network run, where the response matrix fires, and a **violation** against a `--dist` run of the same committed policy, where the rule needs `matrix` and reads `not-collected`. One reviewed file, and whether it broke doctrine 2 depended on which collector the job ran, for a rule that simply was not collected. **The red does not go away, and this does not claim it does**: measured against an otherwise clean `--dist` build, the entry reports one violation and no stale entry before, one stale entry and no violation after, and exit `1` both times — a family C rule can never collect `matrix` off a build directory, so no wording of the entry satisfies both jobs now either. What goes is the state-dependence and the accusation: the operator stops being told their committed policy breaks the doctrine when what happened is that the rule did not fire.

  A rule that emitted nothing now raises no scope problem in either direction. Doctrine 5 already says the true thing about it: a valid entry that silences nothing is reported **stale**, matched by subject or not, which is the honest reading of "this rule did not fire". Stale is red too, so nothing is quietly permitted — an entry's validity is now a property of the rule's finding shape, never of the run.

  **The stale line now says which kind of stale.** Doctrine 5 had one sentence for it — _"silenced nothing in this run — delete it"_ — and this change routes a new case into it: an entry whose rule never ran. Deleting one on that advice un-silences a genuine finding in the job where the rule does collect, which is the opposite of what the line is for. An entry whose rule reached no judgement (`not-collected`, `not-applicable`) now says so, quotes what the kernel said about it, and asks for no deletion; an entry whose rule ran and silenced nothing still asks for one. Read off the `RuleResult`'s verdict, because the finding count is `0` in both.

  **An empty `subject` is refused where it is written.** `{ subject: '' }` parsed, then answered `subjectScopeProblem`'s `subject === undefined` test as though it were the site-wide form while `matches` could never match it — so the entry went red as _stale_, and the operator was told to delete a line whose whole defect was one missing string. It collided in `keyOf` as well, which joins rule and subject, so it and the subject-less entry for the same rule reported as duplicates of each other. `parseEntry` now names the missing page.

  Inert on `apps/marketing/audit-suppressions.json`, which names only `core/inventory-varies-across-pages` — a site rule with site-scoped findings, which takes the same path in both directions.

  **The check's other half was resting on a catalogue property nothing asserted.** `subjectScopeProblem` requires a `subject` when _all_ of a rule's findings are page-scoped and forbids one when _none_ are, which partitions the space only while a rule's findings agree on one scope. A rule emitting a **mix** would answer "no problem" to both tests, and one subject-less entry would sweep its page findings alongside its site ones — the blanket ignore doctrine 2 exists to ban. No rule mixes today, but adding one is an ordinary thing to do: family C's own builder type already carries `scope`, and the failure would be silent, a suppression file quietly widening to cover findings it never named.

  `src/scope-uniformity.test.ts` asserts it over `CORE_RULESET` and the packs, in two halves that between them reach every rule. Statically, no draft anywhere in the catalogue overrides its scope to `site` — checked by **parsing** the catalogue's own source, counting every `scope` property it sets, resolving each through its own file's constants, and matching the site-valued total against the number of site-scoped rules. Whatever does not resolve to a literal — a computed expression, a constant from another module, a `{ scope }` shorthand — is reported rather than skipped, because a scan that misses an assignment reports **zero** and not an error. The file set is the import closure of `ruleset.ts` rather than a directory listing, so a draft shape is read exactly when a rule can reach it. That makes all 35 page-scoped rules uniform by construction, since `gradeFinding` can only ever hand them `draft.scope ?? 'page'`. A regex over `src/rules/*.ts` was the first shape of this and was not exhaustive, which is the one thing it cannot be, since the whole page-scoped half of the catalogue rests on it: a scope written without a trailing comma (`const SITE_WIDE = { scope: 'site' } as const;`, spread into a draft) and a shape declared one directory up both walked past it with the suite green. At runtime, a three-bundle corpus drives all 11 site-scoped rules — the only ones that _can_ mix, since overriding a draft to `page` is exactly what family C does — until each emits a finding, and asserts the scopes agree. The corpus is checked for that reach as well, so a site rule that stops firing fails loudly rather than leaving the half of the catalogue that can actually break this unguarded.

  Both halves were falsified before being trusted: a family C rule made to emit one site-scoped finding beside its page-scoped ones fails the runtime half; a `scope: 'site'` added to a draft in family D fails the static one.

  Docs: `packages/audit/AGENTS.md` and `subjectScopeProblem`'s own comment both said a rule falling silent "never makes a blanket entry legal". The operative point was right and the wording was loose — for a **site**-declared rule that fell silent a blanket entry always was legal, and simply silenced nothing. Both now say what the code does and why, and name the invariant the check rests on.

## 0.1.0

### Minor Changes

- 00d61b3: Start the native shells: render the About tab in SwiftUI, and move the audit into a headless engine every platform can host.

  The Safari wrapper app has been React in a `WKWebView` since it existed, which was right while it was mostly a launcher. It is becoming a tool a site owner runs against their own site, and two things follow. A WebView cannot render platform components — Liquid Glass, Fluent and Material are not CSS, and the tab bar was a `<div role="tablist">` with hand-rolled arrow keys. And an audit report is a long list of expandable rule results, which is the shape native list virtualization handles best and a deep DOM tree handles worst.

  The objection was that identical rendering across platforms is what proves "same evidence, same answer". It is not: that invariant lives in `evaluate()`, a pure function from `Evidence` to `Report` that `purity.test.ts` already enforces. It is a property of the data and it survives any renderer. So the UI goes native per platform and the kernel stays the single source of truth — the split is written up in `docs/native-shells.md`.

  `@movar/audit-engine` is the headless half: the collector, the DOM digest and the kernel in one bundle a shell loads into an offscreen WebView that never renders. It is a system WebView rather than an embedded JS engine because `digest-dom` needs a genuine `Document` — `@movar/lang-pickers` narrows with `instanceof HTMLAnchorElement` on globals, and a shim that is subtly unfaithful returns `not-applicable` on four rules instead of failing loudly, which is a false pass on somebody's audit. HTTP stays native, so `default-src 'self'` keeps forcing every byte of egress through one auditable file; that is now a property of Movar Audit on any platform rather than a quirk of Safari. Two things that were hardcoded to Safari became inputs: the probe is injected, and the collector id is declared by the host, because a run on Android has to say `okhttp` and mean it. The Safari host app is that engine's first consumer rather than a second copy of it: its Audit tab calls `runAudit`, so the collector, the probe contract and the collector's tests exist once — and its reports pick up the engine stamp for free, which a screen adjudicating on its own could not have done.

  Every report now names the build that produced it. `Report` gains an `EngineStamp`, written during `evaluate()` rather than patched on afterwards, because a report exists to be re-adjudicated and "run this evidence again" is unanswerable without knowing which engine judged it the first time. The stamp is optional on the type — `evaluate()` is pure and the CLI and its tests share no build identity, and a pure function cannot learn its own — so each runtime supplies it, which is also what lets one adopt it at a time. A report that carries none renders as _unknown_, never as a default: filling in the running build's version inside the one field whose job is to say which code to go back to would mint an identity nobody shipped, and a wrong answer that looks right sends a reader to the wrong commit.

  The bundle is built and synced into the app's resources by both Safari build paths, and referenced from the Xcode project. That is compliance, not convenience — every store forbids downloading and executing code at runtime, so a future change that fetched the engine from a CDN would be a violation on all three rather than an optimisation.

  Appearance is each platform's canonical stock look, and the drift between platforms is the deliverable rather than a defect. The brand surface that crosses is one accent and the mark; the UI face is the system face, because shipping Manrope would fight Dynamic Type and break the metric alignment stock layouts rely on next to SF Symbols. Two ADR assumptions did not survive contact: `.tint()` is macOS 12 against this app's macOS 11.0 floor, and `SettingsLink` cannot reach Safari's Extensions pane at all — both are corrected in the doc.

  Only About is native so far; Detector, Audit and Settings still render in the WebView behind a native `TabView`, and the web layer stopped drawing its own tab bar so the two do not both appear. **None of the Swift has been compiled or run** — it typechecks for macOS 11 and its localisation and project edits validate, but there is no Xcode on the machine this was written on, the iOS branches got syntax checking only, and re-parenting one `WKWebView` across three SwiftUI containers on tab change is unproven on a device. The VoiceOver announcement the web banner had via `aria-live` is dropped rather than hand-rolled, which is a real regression tracked separately.
